Learn this before doing today’s work

How to use this section: read the six explanations,follow the worked examples,then try the two guided questions. Your teacher will discuss them before assigning independent work. Return to the numbered explanation if you need help with a check question.

1. What Blender does

Blender is the software that holds and changes our editable 3D scene. A scene contains objects and their properties, such as size and location. A screenshot is only a picture of a view; it does not replace the editable scene. The AI can propose a tower, but Blender must actually create and store it.

2. What the human designer does

A requirement says what our design must do. An acceptance test says how we will check that requirement. Students choose requirements, predict results, compare evidence, and propose revisions. The teacher combines selected ideas and reviews computer actions. Watching the screen alone does not show that a student understands the design.

3. A picture is evidence for some claims

A screenshot may show that a visible roof appears blue or that a tower is left of a home. It cannot by itself establish an exact hidden dimension. To check “height is 6 units,” inspect a dimension value or a measurement. To claim a route works for a particular user, define that user’s needs and test the route against them.

4. What AI, MCP, and hardware do

AI suggests an answer or action. MCP is a communication protocol through which an application can call tools made available by a server. In our setup those tools can change Blender, but only if the installed connection supports the requested action. MCP does not supply extra memory or guarantee a correct model. The processor executes instructions, memory holds working data, and storage keeps saved files.

5. Turn a wish into a checkable rule

“Make a wonderful path” is a wish because different people may judge wonderful differently. “The path is at least 2 units wide” names a quantity and a minimum. A checkable rule needs an observable condition, a number, or an explicit relationship. A requirement is a target; it becomes a passed test only after suitable evidence confirms it.

6. Learning continues without a live result

A paper trace follows an algorithm step by step and records its predicted values. It can reveal a mistake before Blender runs. A paper test is useful evidence about your reasoning, but it is not proof that Blender executed correctly. Label work as prediction, actual observation, or simulation so a failed network never forces you to invent a result.

How to use this section: read the six explanations,follow the worked examples,then try the two guided questions. Your teacher will discuss them before assigning independent work. Return to the numbered explanation if you need help with a check question.

1. A dependency means something is needed first

A dependency arrow means one step needs information or an output from another. A roof needs the body’s top height before its own vertical position can be set. An arrow can be labeled “body supplies top height to roof.” It does not mean the roof is prettier or simply nearby. Any order that respects all required inputs can be valid.

2. Inputs, actions, and outputs

An input is information a part uses: tower height and position are inputs. Actions do the work, such as placing a body and roof. Outputs are the resulting named objects or reported values. A module contract records its job, inputs, outputs, dependencies, and tests. This tells another designer enough to build and check the part.

3. Abstraction keeps the relevant detail

Abstraction means leaving out details that do not help the current problem while preserving those that do. To plan a walking route, a house’s footprint, location, and height clearance can matter; tiny roof shingles usually do not. A rectangle is a useful stand-in for the footprint. Omitting its width would remove relevant information, not improve the abstraction.

4. Names let us change the intended part

A stable name such as Tower_body identifies one object across revisions. “Change Tower_body height to 8” is more precise than “change that thing.” Before creating a named object, check whether it already exists; updating it avoids accidental duplicates. Names are identifiers, not proof that the named object has the right values.

5. Bridge span depends on the river

Span is the distance the bridge must cover. If the river boundaries are x=-1 and x=1, the water width is 1-(-1)=2 units. We must know those boundaries before checking a bridge crossing. In our class world the river boundaries will be -2 and 2. A bridge may extend beyond both banks; knowing just its center cannot prove it spans the water.

6. Decomposition supports implementation

Decomposition divides a large problem into parts that can be designed, built, and checked. Listing “tower, bridge, home” is a start. Giving each part inputs, responsibilities, outputs, and tests makes the plan usable by a program. Submodules can divide a tower into body and roof. A shared interface states the information one part supplies to another, such as body_top.

How to use this section: read the six explanations,follow the worked examples,then try the two guided questions. Your teacher will discuss them before assigning independent work. Return to the numbered explanation if you need help with a check question.

1. Center, height, top, and bottom

The center is halfway between an object’s top and bottom. For height h and center z=c, bottom=c-h/2 and top=c+h/2. To rest on ground g, center=g+h/2. Half-height is needed because the object extends both above and below its center. These rules describe our simple upright bodies, not arbitrary rotated meshes.

2. Footprint edges use half the width

A footprint is the top-down area an object occupies. For center x and width w, left edge=x-w/2 and right edge=x+w/2. Do the same with y and depth. Checking only a center can miss an edge crossing a river or the terrain boundary. Write negative numbers carefully: -6-2=-8, while -6+2=-4.

3. Our coordinate convention

Coordinates are ordered x,y,z. On our planning map x increases east, y increases north, and z increases upward. Ground top is z=0. The tower center (-7,4,4) means west of the origin, north of the origin, and 4 units upward. A minus sign is a direction relative to the origin, not automatically an invalid position.

4. A precise prompt supplies executable detail

A prompt should say what to keep, which named objects to create or update, dimensions, center positions, and what to report. “Tall and nearby” leaves height and distance undecided. Natural-language instructions can still be misunderstood, so include acceptance tests. A clear request reduces ambiguity but never eliminates the need to inspect the result.

5. Separate requirement, prediction, and observation

A requirement is what we want. A prediction is what we expect the instructions to produce. An observation is what we actually inspect or measure. An unverified AI statement is a claim, even if it repeats our desired number. Put unknown in the result column when suitable evidence is unavailable; do not copy the requirement into that column and call it measured.

6. A separate roof needs its own center

When a roof of height r sits on a body top t, roof center=t+r/2. Roof bottom must equal t for contact. For our simple body, t=ground+body_height. A roof centered at the body top would extend partly inside the body. Record roof bottom and top to distinguish contact, gap, and overlap.

1. A span is end minus start

Distance on a number line is right endpoint minus left endpoint. A span from -3 to3 is 3-(-3)=6 units, not zero. Adjacent planks meet when one right edge equals the next left edge. For 1-unit planks, each edge lies half a unit from its center. Count distinct positions as well as objects.

3. A sequence and its trace
